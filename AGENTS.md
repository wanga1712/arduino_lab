# Правила разработки Arduino Lab

Эти правила обязательны для всех изменений в репозитории.

## Перед выполнением задачи

1. Прочитать `README.md`, `IMPLEMENTATION_PLAN.md` и `docs/ARCHITECTURE.md`.
2. Проверить управляющие файлы `WIP`, `WIP.md`, `docs/WIP`, `docs/WIP.md`.
3. Выполнить целевой поиск через `rg --files` и `rg` только в затрагиваемой области.
4. До создания функции, типа, компонента, endpoint, схемы или константы найти существующие реализации с тем же назначением.
5. Проверить публичные экспорты пакетов и направления импортов.
6. В отчёте указать, что было найдено и почему существующий модуль переиспользован, расширен либо признан неподходящим.

Нельзя начинать новый модуль со слов «проще написать заново» без проверки существующего кода.

## Ограничение размера

- Каждый рукописный модуль содержит не более 150 физических строк, включая пустые строки и комментарии.
- Правило относится к `.ts`, `.tsx`, `.js`, `.jsx`, `.css`, `.scss`, `.sql` и исполняемым скриптам.
- Тестовый файл также считается модулем и ограничен 150 строками.
- Исключения: lock-файлы, сгенерированные файлы, конфигурация инструментов и документация Markdown.
- Исключение для исходного кода возможно только через заранее согласованную запись в `docs/decisions/`; скрывать превышение запрещено.
- При приближении к лимиту модуль делится по ответственности, а не на случайные `helpers`.

## Единственность ответственности

- Одна функция продукта имеет одну каноническую реализацию.
- Нельзя дублировать доменные типы, API-контракты, runtime-схемы, правила валидации, формулы, тексты диагностик и константы.
- Похожую реализацию сначала расширяют или обобщают. Копирование с переименованием запрещено.
- Нельзя создавать общие `utils`, `helpers` или `common` без чётко определённого владельца и назначения.
- UI не повторяет правила доменного слоя, API не повторяет валидатор цепи, repository не содержит бизнес-решений.
- Запрещены циклические зависимости.

## Границы проекта

- `packages/shared` — единственный владелец общей предметной модели, Blink-контрактов и API DTO.
- `packages/shared` не импортирует код из `apps`.
- `apps/web` может импортировать публичные экспорты `packages/shared`, но не внутренности `apps/api`.
- `apps/api` может импортировать публичные экспорты `packages/shared`, но не код `apps/web`.
- В API направление зависимостей: route → service → repository → database driver.
- Route отвечает за HTTP, service — за сценарий, repository — за хранение, driver — за PostgreSQL.
- `circuit` остаётся чистым TypeScript без React, HTTP, PostgreSQL, таймеров и browser API.
- React-компоненты не выполняют SQL, доменный обход графа или разбор Arduino C++.
- SQL-схема изменяется только новой последовательной миграцией; применённая миграция не переписывается.
- Опубликованные курсы, уроки, компоненты, датчики и их пины берутся из PostgreSQL; production-описания не дублируются в web.
- Новый датчик использует общий каталог и версионированные метаданные; отдельная таблица на тип датчика требует заранее согласованного ADR.
- PostgreSQL хранит `rule_key` и параметры, но реализация электрического правила существует только в `packages/shared/src/circuit`.
- Production-секреты не попадают в Git, frontend bundle, URL и журналы.

## Согласование модулей

- Связь пакетов выполняется через типизированные публичные контракты.
- Новый публичный контракт сначала добавляется владельцу домена, затем используется потребителями.
- Изменение контракта сопровождается обновлением всех потребителей в том же шаге.
- Нельзя импортировать приватный файл другого feature в обход его публичного `index.ts`.
- Ошибки имеют стабильный машинный код; UI отображает их, но не определяет бизнес-логику по тексту.
- Сервер и клиент используют одну версию сериализуемого состояния из `packages/shared`.

## Git и документы

- Кодер не выполняет `push`, не меняет remote и не переписывает историю.
- `README.md`, `LICENSE`, `.gitignore`, `AGENTS.md`, релизные коммиты и push ведёт ревьюер проекта.
- Кодер не включает изменения следующего этапа в текущий коммит.
- Секреты, дампы PostgreSQL, ключи и локальные `.env` нельзя добавлять даже временно.

## Проверка перед приёмкой

Ревьюер проверяет:

1. поиск существующей реализации до добавления новой;
2. размер каждого изменённого рукописного модуля;
3. дублирование функций, типов, констант и схем;
4. направления импортов и отсутствие циклов;
5. согласованность shared-контрактов со всеми потребителями;
6. отсутствие бизнес-логики в UI/routes/repositories;
7. соответствие изменения только текущему шагу;
8. фактические результаты целевых проверок из плана.

Изменение не принимается, пока нарушены лимит, границы или правило единственной реализации.
