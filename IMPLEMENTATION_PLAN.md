# План внедрения WIP-001 — Arduino Lab

## 1. Как работаем

Реализация идёт небольшими законченными шагами. Один шаг — один отдельный коммит без примеси следующего этапа. После каждого шага кодер передаёт:

- commit SHA или полный diff;
- список изменённых файлов;
- краткое описание фактически работающего сценария;
- команды и результаты только тех проверок, которые относятся к шагу;
- известные ограничения и спорные решения.

После этого изменение проходит ревью. Следующий шаг начинается только после исправления замечаний уровня blocker/major. Кодер не редактирует `README.md`, `LICENSE`, `.gitignore` и `AGENTS.md`: их ведёт ревьюер. Коммиты этапов, настройку remote и push также выполняет ревьюер. Развёртывание выполняется только на выделенном шаге 9.

Перед созданием любого модуля кодер обязан найти существующую реализацию той же функции. Каждый рукописный исходный или тестовый модуль ограничен 150 физическими строками. Полные правила и границы находятся в `AGENTS.md` и `docs/ARCHITECTURE.md`.

## 2. Решения, которые фиксируем заранее

- Проект — npm-workspace с тремя границами: React-клиент, Node.js API и общий пакет доменных типов. Клиент собирается Vite и обслуживается вместе с API под одним HTTPS-доменом.
- Backend WIP-001 — небольшой TypeScript-сервис на Fastify. Он сохраняет лабораторные сессии и прогресс, но не исполняет Arduino C++ и не подменяет клиентский Blink-движок.
- Основное серверное хранилище — PostgreSQL. Доступ выполняется через параметризованные запросы `pg`, а схема изменяется последовательными SQL-миграциями, которые хранятся в репозитории.
- Весь стек разворачивается на Ubuntu-сервере №13: reverse proxy с HTTPS, web/API и PostgreSQL. Конкретные host/IP, домен, SSH-пользователь и способ выдачи сертификата должны быть переданы отдельно и не записываются в репозиторий как секреты.
- Для редактора выбираем CodeMirror 6: он легче и модульнее Monaco, а для одного учебного C++-шаблона возможностей достаточно.
- Электрическая модель, UI-координаты и представление SVG не смешиваются. Валидатор работает только со стабильными ID контактов и netlist.
- Опубликованные курсы, уроки, шаги и каталог компонентов хранятся в PostgreSQL по ADR-001. API собирает их в типизированный `LessonDefinition`; в WIP-001 существует только `blink`, универсальный редактор контента не создаём.
- Проверка схемы возвращает структурированные диагностические сообщения с уровнями `error`, `warning`, `info` и стабильными кодами. UI не анализирует текст сообщений.
- «Запустить» доступно только после успешной проверки схемы и поддерживаемого Blink-кода. Любое изменение схемы или кода инвалидирует предыдущую проверку и останавливает симуляцию.
- Blink-движок разбирает только явно документированный шаблон. Он не называется компилятором или полноценным эмулятором Arduino.
- Состояние хранится в версионированном JSON. `localStorage` используется как локальный кэш и аварийное восстановление, PostgreSQL — как серверное хранилище. Декодирование данных из обоих источников считается недоверенным.
- В WIP-001 нет пользовательских аккаунтов. Анонимная сессия получает случайный идентификатор и отдельный секрет редактирования; в PostgreSQL хранится только хеш секрета. Секрет не попадает в URL и журналы.
- Серверная синхронизация использует номер ревизии: конфликт не перезаписывает более новую запись молча, а возвращает клиенту явный `409 Conflict`.
- В MVP поддерживается одна экземплярная цепь: один LED и один резистор. Модель остаётся типизированной и расширяемой, но множественные цепи и произвольная электроника не входят в объём.
- Визуальные признаки полярности, выбранного контакта, ошибок и состояния LED не должны зависеть только от цвета.

## 3. Пошаговая реализация

### Шаг 0. Репозиторий и воспроизводимый каркас

Задача кодеру:

- проверить управляющие инструкции, созданный архитектурный каркас и существующие исходники;
- убедиться, что Node.js и npm доступны; при отсутствии установить официальный Node.js LTS через `winget`, обновить `PATH` текущего процесса и продолжить;
- сохранить существующую Git-ветку `feature/wip-001-arduino-lab-mvp`, не выполнять push и не менять remote;
- создать npm-workspace с `apps/web`, `apps/api` и `packages/shared` без демонстрационного мусора;
- создать Vite + React + TypeScript клиент и минимальный Fastify API;
- включить строгую проверку TypeScript, добавить lock-файл и Windows-совместимые npm-скрипты;
- настроить Vitest + React Testing Library и один минимальный smoke-тест загрузки оболочки;
- добавить кроссплатформенный `npm run check:architecture` для лимита 150 строк, запрещённых/циклических импортов и поиска технических дублей;
- создать маршрут/точку входа `/lab?lesson=blink`, а неизвестный урок обрабатывать понятным экраном ошибки;
- добавить `GET /api/health/live` без обращения к БД и каркас `GET /api/health/ready` для будущей проверки PostgreSQL;
- не добавлять state manager, редактор кода и библиотеку маршрутизации до реальной необходимости.

Критерии приёмки:

- корневые `npm install`, `npm run dev`, `npm run build`, `npm run test` определены для workspace и не используют Unix-команды;
- TypeScript работает в strict-режиме;
- по целевому URL открывается пустая оболочка лаборатории, а не готовая фиктивная схема;
- код и конфигурация не содержат CDN и чужой графики.
- `npm run check:architecture` отклоняет намеренно созданное превышение лимита и запрещённый импорт;
- каждый добавленный модуль имеет одного владельца из `docs/ARCHITECTURE.md`.

### Шаг 1. Чистая доменная модель breadboard и цепи

Задача кодеру:

- создать независимый от React модуль `src/circuit/`;
- определить типы стабильных ID для контактов UNO, отверстий breadboard, выводов компонентов, проводов и компонентов;
- описать реальную топологию: группы по пять отверстий, разрыв по центру, отдельные и явно сегментированные шины питания;
- реализовать построение электрических узлов/netlist из топологии, проводов, резистора и LED;
- исключить координаты SVG и подписи интерфейса из доменных вычислений;
- покрыть узкими unit-тестами соединённые и несоединённые группы.

Критерии приёмки:

- одинаковый электрический результат получается независимо от расположения элементов на экране;
- разные ряды, две половины breadboard и независимые шины не соединяются случайно;
- UNO не соединён с шинами питания без провода;
- элементы представлены рёбрами между узлами, LED сохраняет направление анод → катод.

### Шаг 2. Валидатор схемы и учебная физика

Задача кодеру:

- отдельно от netlist реализовать валидатор последовательного пути от цифрового пина до GND;
- распознавать корректную перестановку LED и резистора в последовательной цепи;
- добавить диагностические коды для отсутствия GND, разрыва/неверного ряда, обратной полярности, отсутствия резистора, слишком малого сопротивления, короткого замыкания 5V–GND и несовпадения пина;
- вынести допущения физической модели в именованные константы: 5 В HIGH, 2 В падение на красном LED;
- рассчитывать ориентировочный ток `(5−2)/R`;
- зафиксировать границы: менее 150 Ом — опасная ошибка, 150–219 Ом — допустимо с предупреждением, 220–330 Ом — рекомендуемый диапазон, выше 330 Ом — допустимо с информацией о меньшей яркости;
- покрыть каждую ветку валидатора unit-тестом, включая ток около 13,6 мА для 220 Ом.

Критерии приёмки:

- успех определяется обходом графа, а не числом проводов, координатами или заранее известной раскладкой;
- короткое замыкание имеет приоритет над сообщением об успехе;
- сообщения содержат детский текст, но логика опирается на диагностический код;
- предупреждения и ошибки различаются явно.

### Шаг 3. Конфигурация урока и локальное состояние

Задача кодеру:

- определить минимальные `LessonDefinition`, `ComponentDefinition`, `CircuitValidationResult`, `Sketch` и состояние запуска;
- определить runtime-схему `LessonDefinition`: текст задания, шаги, начальный скетч, допустимые компоненты, целевой пин и декларативные критерии успеха;
- использовать тестовую fixture Blink только для проверки доменной модели; production-конфигурацию урока не хардкодить в web;
- добавить единое типизированное хранилище; Zustand использовать только если оно упрощает атомарные операции и подписки;
- реализовать команды добавления/удаления LED, резистора и провода, изменения сопротивления, сброса и выбора контакта;
- реализовать локальный кэш под ключом с версией формата и безопасное восстановление через runtime-проверки;
- не сохранять производные данные netlist, результаты проверки и работающие таймеры.

Критерии приёмки:

- повреждённый JSON и неизвестная версия не роняют приложение;
- сброс удаляет сохранение только текущего урока;
- идентификаторы остаются стабильными после перезагрузки;
- изменение схемы сбрасывает результат прежней проверки.

### Шаг 4. API и PostgreSQL

Задача кодеру:

- подключить PostgreSQL через `pg` и только параметризованные запросы;
- добавить версионированные SQL-миграции и отдельного непривилегированного пользователя приложения;
- реализовать минимальную схему ADR-001 для `courses`, `course_modules`, `lessons`, `lesson_revisions`, `lesson_steps`, `component_definitions`, `component_revisions`, `component_pins`, `lesson_components` и `lesson_rules`;
- добавить идемпотентный seed для одного курса/модуля, Blink-урока, Arduino Uno, LED и резистора без будущих датчиков;
- создать таблицу лабораторных сессий минимум с полями `id`, `lesson_slug`, `state_version`, `state_json`, `sketch_text`, `revision`, `edit_token_hash`, `created_at`, `updated_at`;
- хранить электрическую модель в проверяемом `JSONB`, а пользовательский Arduino-скетч — как точный `TEXT` без нормализации;
- реализовать создание, чтение и обновление анонимной сессии; изменение требует секрета в заголовке, а в БД хранится только криптографический хеш;
- проверять lesson slug, версию, размер текста и структуру состояния на границе API;
- ограничить размер тела запроса, не писать скетч и секрет в access/error logs;
- реализовать optimistic locking через `revision` и ответ `409` при конфликте;
- реализовать readiness-проверку БД и graceful shutdown пула соединений;
- реализовать `GET /api/lessons/:slug`, который собирает опубликованную ревизию в общий `LessonDefinition` и отклоняет неизвестные `rule_key`;
- добавить интеграционные тесты API на отдельной тестовой БД, не подменяя PostgreSQL SQLite или in-memory-хранилищем.

Критерии приёмки:

- миграции применяются повторяемо к пустой PostgreSQL и имеют документированный порядок;
- сессия переживает перезапуск API и читается из БД;
- неверный/отсутствующий секрет не позволяет изменить запись;
- устаревшая ревизия не перезаписывает новые данные;
- повреждённый JSON, слишком большой скетч и неизвестная версия отклоняются с безопасной ошибкой;
- SQL-инъекция через поля запроса невозможна благодаря параметризации;
- Blink загружается из PostgreSQL через API, а неизвестный урок и несовместимая ревизия возвращают стабильные ошибки;
- опубликованная ревизия урока и компонента не изменяется задним числом.

### Шаг 5. SVG-рабочее поле и честное редактирование схемы

Задача кодеру:

- собственными SVG-примитивами нарисовать узнаваемые UNO и breadboard с подписями D0–D13, 5V, GND, рядов и шин;
- отрисовать LED с различимыми анодом/катодом, резистор и провода;
- реализовать предсказуемый сценарий «выбрать компонент/провод → выбрать контакты»; drag-and-drop не обязателен;
- дать добавление, выбор и удаление элементов, изменение номинала, отмену незавершённого соединения;
- отображать стабильные имена обоих концов провода и подсвечивать выбранный контакт;
- предусмотреть доступные кнопки/подписи, видимый focus и признаки, не основанные только на цвете;
- не помещать правила электрической проверки в React-компоненты.

Критерии приёмки:

- пользователь действительно собирает цепь с пустого поля;
- клики меняют доменную модель, после перезагрузки раскладка восстанавливается;
- провод невозможно создать с несуществующим или одним концом;
- элементы можно удалить без висячих ссылок;
- интерфейс остаётся понятным при ширине Stepik iframe 800–1100 px.

### Шаг 6. Редактор и узкий BlinkExecutionEngine

Задача кодеру:

- подключить CodeMirror 6 с локально установленными пакетами и подсветкой C++;
- определить интерфейс `CodeExecutionEngine` и реализацию `BlinkExecutionEngine`;
- реализовать разбор поддерживаемого шаблона с `ledPin`, `pinMode(..., OUTPUT)`, чередованием `digitalWrite(HIGH/LOW)` и двумя положительными `delay`;
- корректно игнорировать пробелы и комментарии, но отклонять неоднозначные, неполные и произвольные конструкции;
- ввести безопасные границы задержки, например 50–60 000 мс, с явным сообщением;
- реализовать скачивание `.ino` байт-в-байт из текущего текста редактора;
- показать рядом с редактором постоянную честную границу поддержки.

Критерии приёмки:

- изменение `ledPin` и обоих `delay` меняет разобранный план исполнения;
- неизвестный синтаксис не приводит к фиктивному запуску;
- несовпадение пина кода и схемы выдаёт отдельную диагностику;
- скачанный файл содержит именно пользовательский текст, без нормализации и подмены;
- парсер и скачивание покрыты узкими тестами.

### Шаг 7. Оркестрация проверки, синхронизации и симуляции

Задача кодеру:

- связать конфигурацию урока, валидатор схемы и Blink-движок через прикладной слой;
- связать локальный кэш с API: первая запись создаёт серверную сессию, последующие изменения синхронизируются с ревизией;
- при недоступности сервера не терять локальную работу, явно показывать статус «сохранено локально» и повторять синхронизацию без бесконечного частого polling;
- конфликт ревизий показывать пользователю и не разрешать молчаливую перезапись;
- реализовать кнопки «Проверить схему», «Запустить», «Остановить», «Сбросить», «Скачать .ino» с корректными disabled-состояниями;
- запускать визуальное мигание только для проверенной схемы и разобранного кода;
- использовать фактические HIGH/LOW и задержки из пользовательского текста;
- очищать таймеры при остановке, сбросе, изменении данных и размонтировании;
- показывать список конкретных ошибок и предупреждений, а не один общий статус.

Критерии приёмки:

- корректная цепь на D9 и стандартный скетч мигают с периодом из кода;
- изменение задержек заметно меняет период;
- неправильная схема, другой пин и неподдерживаемый код блокируют запуск;
- после остановки и ухода со страницы активных таймеров не остаётся;
- изменение уже проверенной схемы требует новой проверки.
- перезагрузка страницы восстанавливает локальное состояние, а доступная серверная сессия подтверждает актуальную ревизию;
- временная недоступность API не блокирует сборку и запуск схемы.

### Шаг 8. Адаптивность, embed-режим и документация продукта

Задача кодеру:

- собрать три зоны лаборатории на широком экране и последовательный адаптивный вид на узком;
- реализовать `embed=1` без обращения к `window.top` и без сторонних cookies;
- убрать в embed-режиме только второстепенную шапку, сохранив все действия урока;
- добавить `docs/STEPIK.md` с HTTPS URL, iframe-примером, рекомендуемыми размерами и запасной ссылкой в новую вкладку;
- добавить `docs/ROADMAP.md` с WIP-002…WIP-005 и честными границами текущей версии;
- не добавлять авторизацию Stepik или Web Serial;
- описать серверное сохранение отдельно от отсутствующей пользовательской регистрации.

Критерии приёмки:

- в обычном и embed-режиме доступен полный учебный сценарий;
- текст не создаёт горизонтальную прокрутку;
- документация не обещает AVR-эмуляцию, автоматические оценки Stepik или прошивку платы;
- все внешние ограничения названы явно.

### Шаг 9. Развёртывание полного стека на сервере №13

До начала шага должны быть известны host/IP сервера №13, SSH-порт и пользователь, домен, доступный способ управления DNS, политика firewall и разрешённый способ установки сервисов.

Задача кодеру:

- сначала проверить существующие сервисы, порты, reverse proxy, PostgreSQL и правила развёртывания сервера, не перезаписывая чужую конфигурацию;
- подготовить воспроизводимое развёртывание web, API и PostgreSQL на одном сервере; Docker Compose предпочтителен, если сервер уже допускает Docker, иначе использовать systemd и существующий PostgreSQL;
- держать PostgreSQL недоступным из публичной сети, создать отдельные БД/роли приложения и миграций с минимальными правами;
- хранить production-секреты только на сервере; в репозитории оставить `.env.example` без значений;
- настроить reverse proxy: web и `/api` на одном HTTPS origin, корректные security headers, лимит тела запроса и проксирование клиентского IP;
- настроить применение миграций как отдельную контролируемую операцию до переключения новой версии;
- добавить healthcheck, перезапуск API после сбоя, ротацию журналов и проверку свободного места;

## 5. Формат запроса на ревью

После каждого шага достаточно прислать:

