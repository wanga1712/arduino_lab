# ADR-001 — учебная структура и компоненты в PostgreSQL

**Статус:** принято 2026-10-27

## Контекст

Arduino Lab должен расширяться от одного Blink-урока до курсов с датчиками и исполнительными устройствами. Жёстко заданные в React уроки, расползание описаний пинов по коду и отдельная таблица для каждого датчика приведут к дублированию и сложным обновлениям.

## Решение

PostgreSQL является источником опубликованных данных о курсах, уроках и каталоге компонентов. API собирает эти данные в версионированный `LessonDefinition`, проверяемый общими runtime-схемами из `packages/shared`.

### Реляционная учебная структура

- `courses` — курс, slug, название и статус публикации;
- `course_modules` — упорядоченные разделы курса;
- `lessons` — урок и его текущая опубликованная версия;
- `lesson_revisions` — неизменяемые версии задания и настроек;
- `lesson_steps` — упорядоченные объяснения и действия;
- `lesson_prerequisites` — зависимости между уроками.

Опубликованная ревизия не переписывается. Исправление создаёт новую ревизию, поэтому сохранённая работа ученика остаётся воспроизводимой.

### Каталог плат и датчиков

- `component_definitions` — стабильная сущность: Arduino Uno, LED, резистор, датчик;
- `component_revisions` — версия электрических и визуальных метаданных;
- `component_pins` — стабильный ключ пина, назначение, направление, протокол и допустимые электрические параметры;
- `lesson_components` — доступные в уроке ревизии компонентов, их alias, количество и стартовые параметры;
- `lesson_rules` — ключ реализованного валидатора и проверяемые параметры `JSONB`.

Для нового типа датчика не создаётся отдельная таблица. Отличающиеся характеристики хранятся в версионированных метаданных, а общие электрические свойства и пины остаются типизированными колонками.

### Подключения

PostgreSQL хранит допустимые компоненты, описание пинов и декларативные требования урока. Например, `rule_key = series_path` с параметрами целевого пути или `rule_key = pin_protocol` с требуемым I2C/PWM.

База не исполняет SQL-правила электрической проверки и не хранит JavaScript. `rule_key` обязан соответствовать единственной реализации в `packages/shared/src/circuit`; неизвестный ключ отклоняется при публикации и загрузке урока.

Фактически собранная учеником схема хранится в `lab_sessions.state_json` как версионированный снимок: компоненты, стабильные ID пинов и провода. Netlist и результаты проверки не сохраняются как истина, а пересчитываются доменным модулем.

## Границы ответственности

- PostgreSQL: содержание, порядок, версии, каталог и параметры правил.
- API repository: чтение/запись строк без бизнес-решений.
- API service: сборка опубликованного `LessonDefinition` и контроль ревизий.
- `packages/shared`: типы, runtime-проверка, netlist и реализация `rule_key`.
- Web: отображение полученного определения и пользовательской схемы.

Web никогда не обращается к PostgreSQL напрямую. API не копирует электрические формулы и не интерпретирует схему самостоятельно.

## Объём WIP-001

В первой версии миграции и seed создают один курс/модуль, Blink-урок, Arduino Uno, LED и резистор. Схема уже допускает будущие датчики, но их UI, симуляция и уроки до WIP-003 не реализуются.

## Последствия

Плюсы: контент меняется без пересборки frontend, версии воспроизводимы, датчики имеют единый каталог, правила не дублируются.

Цена: API и миграции становятся обязательными для опубликованных уроков; нужны runtime-проверка JSONB, seed-данные и контроль совместимости ревизий.
